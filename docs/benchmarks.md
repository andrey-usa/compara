## Method

Each pair is written by `compara-gen-data` (seed 7). The headline pairs have no key twice in a file (`--unique-keys`); the others are the generator's default, where 0.01% of a file's keys appear twice (rows otherwise the same). Parquet comes from three writers, and every tool reads the same files: compara-gen-data's own (every column a string, uncompressed), and, on the unique-key pairs, the generator's CSV pair as Polars (`pl.read_csv(csv).write_parquet(out)`) and DuckDB (`COPY (SELECT * FROM read_csv(csv)) TO out (FORMAT parquet)`) write it with their defaults: their own type inference, compression and row groups, in a process of their own before any timing. As file A of each pair holds it:

- 1M rows, Parquet by compara-gen-data, 161 MB: uncompressed, 1 row group, every column a string.
- 1M rows, Parquet by Polars, 61 MB: zstd, 12 row groups, typed columns: amount, fee, balance, rate DOUBLE; quantity BIGINT, the rest strings.
- 1M rows, Parquet by DuckDB, 97 MB: snappy, 9 row groups, typed columns: posting_date, value_date DATE; amount, fee, balance, rate DOUBLE; quantity BIGINT; updated_at TIMESTAMP, the rest strings.
- 1M rows, Parquet by compara-gen-data, repeated keys, 161 MB: uncompressed, 2 row groups, every column a string.
- 10M rows, Parquet by compara-gen-data, 1,609 MB: uncompressed, 10 row groups, every column a string.
- 10M rows, Parquet by Polars, 609 MB: zstd, 114 row groups, typed columns: amount, fee, balance, rate DOUBLE; quantity BIGINT, the rest strings.
- 10M rows, Parquet by DuckDB, 964 MB: snappy, 81 row groups, typed columns: posting_date, value_date DATE; amount, fee, balance, rate DOUBLE; quantity BIGINT; updated_at TIMESTAMP, the rest strings.
- 10M rows, Parquet by compara-gen-data, repeated keys, 1,609 MB: uncompressed, 11 row groups, every column a string.

Before each run the files that tool reads are put in a stated page-cache state: warm, read to the end just before the run; cold, dropped from the page cache (`posix_fadvise` DONTNEED), so the tool reads them from the runner's disk. The state is set for every tool alike, so no tool starts warmer because of what the one before it did (in runs before this was done, a tool killed for memory left the next one's inputs evicted: compara's 10M-row CSV took 0.70 s in one round and 9.33 s in the next, run 44629611468). Each run records the share of its inputs in the page cache as it starts and its major page faults. Each round also times reading both inputs from a cold cache, the least any tool's cold run can take. Each tool runs in a process of its own; CPU time and peak RSS are that process's (`wait4`). Peak RSS counts the pages of files a tool maps, which the kernel can drop and read again under memory pressure: compara maps both inputs, so most of its RSS is the files themselves. The private part is the tool's own memory (heap, stacks; `RssAnon` of its process tree, sampled every 5 ms, so a lower bound), what a container limit has to leave it. Each tool computes what compara does: values compared as text in CSV and by value in Parquet (in the file's types), and an empty field equal only to an empty field. Where no key repeats, each runs its plainest query: DuckDB reads each file where it is (`read_csv(..., all_varchar = true)` or `read_parquet`) and counts over a FULL OUTER JOIN on the key; Polars scans both (`scan_csv(infer_schema=False)` or `scan_parquet`) and counts over a full join, on its default engine, which its streaming engine did not beat; qsv runs `qsv diff -k account_id,txn_id` on the files with the ignored column cut (`qsv select`, untimed), its output written to a file and the counts read back from it, unchanged being the left file's rows (`qsv count`) less the changed and removed; ClickHouse runs `clickhouse local` with the files read where they are (`file`, CSV as String columns), a FULL OUTER JOIN on the key with `join_use_nulls = 1`, so a row missing from one side has NULLs there, and a NULL counted equal only to a NULL; every tool on every core. Where keys repeat, a key that appears twice in a file is compared by its first row, and the other tools have to be told so: DuckDB loads each CSV into a table once for a row order and keeps each key's first row (`QUALIFY row_number()` by `rowid`; on Parquet by `file_row_number`, read in place), Polars adds `unique(keep="first")`, and qsv, whose keys must be unique, is given each key's first row by `qsv extdedup`, untimed. ClickHouse is not run there. The run fails unless every tool that finishes gives the same counts: 1M rows, CSV, 368 MB: 938,951 unchanged, 60,049 changed, 1,000 added, 1,000 removed; 1M rows, Parquet by compara-gen-data, 161 MB: 938,951 unchanged, 60,049 changed, 1,000 added, 1,000 removed; 1M rows, Parquet by Polars, 61 MB: 938,951 unchanged, 60,049 changed, 1,000 added, 1,000 removed; 1M rows, Parquet by DuckDB, 97 MB: 938,951 unchanged, 60,049 changed, 1,000 added, 1,000 removed; 1M rows, CSV, repeated keys, 368 MB: 938,951 unchanged, 60,049 changed, 1,000 added, 1,000 removed; 1M rows, Parquet by compara-gen-data, repeated keys, 161 MB: 938,951 unchanged, 60,049 changed, 1,000 added, 1,000 removed; 10M rows, CSV, 3,679 MB: 9,390,680 unchanged, 599,320 changed, 10,000 added, 10,000 removed; 10M rows, Parquet by compara-gen-data, 1,609 MB: 9,390,680 unchanged, 599,320 changed, 10,000 added, 10,000 removed; 10M rows, Parquet by Polars, 609 MB: 9,390,680 unchanged, 599,320 changed, 10,000 added, 10,000 removed; 10M rows, Parquet by DuckDB, 964 MB: 9,390,680 unchanged, 599,320 changed, 10,000 added, 10,000 removed; 10M rows, CSV, repeated keys, 3,679 MB: 9,390,680 unchanged, 599,320 changed, 10,000 added, 10,000 removed; 10M rows, Parquet by compara-gen-data, repeated keys, 1,609 MB: 9,390,680 unchanged, 599,320 changed, 10,000 added, 10,000 removed.
